# K3 and GLM on actual engine tasks

The CTO wants lower provider cost without a blind quality downgrade. Previous
three-case synthetic comparisons favored K3 over Haiku but did not exercise
actual trained memory/task prompts. Sonnet/Opus are quality references, not the
intended default. Evaluate K3 and GLM with the same real inputs and production
prompt construction before recommending role models.

Use three short real email threads from the authorized company profile, with
trained prompts and expected facts/tasks recorded before model outputs. Keep
mail, prompts and raw responses in a private scratch directory, never public
Git. Execute only the engine API adapter with an isolated SQLite allowance:
USD1 for the complete experiment, conservative pre-call reservations, provider
price caps, no automatic retries/fallback and no reset of uncertain holds.
Company OpenRouter key stays in its existing secret file and process memory.
No writes to production mail, memory, tasks, model settings or pause controls.

Grade answers blinded to model/cost; separately check completion and compatibility
with actual parsers. Report per-task consequential mistakes, hallucinations,
missed commitments, cost and limitations. Passing a small sample is not proof
of zero errors or permission to resume backlogs. Existing production holds are
outside this isolated experiment and must not be discarded to enable it.

The CTO subsequently authorizes prompt improvements when evidence warrants them.
First capture the unchanged baseline. Evaluate any candidate on the same inputs
inside the same USD1 ledger; preserve company rules and output contracts. Do not
apply an unvalidated prompt to production or resume processing as a side effect.
